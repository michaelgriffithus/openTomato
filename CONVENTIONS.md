# OpenTomato Conventions

This is the single source of truth for anyone working in this
repo.

## What OpenTomato is

A small, honest layer between the sensors a home tomato grower already has in
Home Assistant and the published temperature / humidity / VPD windows for each
stage of a tomato plant. It records readings while the app is open, shows whether
the grow space is in range for the current stage, and keeps a simple journal.

It deliberately does **not** rate, score, predict, or diagnose. There is one tier,
no accounts, no cloud of its own. The optional assistant uses the grower's own
API key and sends only a short, visible context block.

## Vocabulary

Say **grow space** (not a hardware-flavoured name), **variety**, **assistant**,
**inspect**, **boundary case**, and **predictions** (as in "no predictions"). Stage
names are exactly: seedling, vegetative, flowering, fruit set, ripening,
harvesting. The list of words and identifiers that must never appear in this
repo lives in `tool/leak_scan.sh`; that script is the authority, so this document
does not repeat it.

Run the scan before every commit (the `.githooks/pre-commit` hook does; enable it
with `git config core.hooksPath .githooks`).

## Engineering rules

- Inspect before changing. Do not invent files, models, or services.
- Screens render from an immutable `*Contract`; only the screen root reads
  providers. Sub-widgets are plain `StatelessWidget`s so they can be tested from a
  contract with no `ProviderScope`.
- Prefer small, surgical changes. Split first when a file nears its cap.
- Every `Future`-returning call is awaited or wrapped in `unawaited(...)`.
- Do not edit generated files (`*.g.dart`); they are git-ignored and rebuilt.
- Single quotes, trailing commas, `const` where possible (`analysis_options.yaml`).
- No AI attribution anywhere: no co-author trailers naming a tool and no
  "generated by" footers, in commits, PRs, comments, code, or docs.

## Size caps (hard)

| File type | Max lines |
|---|---|
| Screen / widget | 400 |
| Provider | 300 |
| Service / repository | 300 |
| DAO | 200 |

`tool/size_caps.sh` checks these.

## Database

- Schema lives in `lib/core/database/database.dart`. The pubspec build number
  MUST equal `AppDatabase.schemaVersion` (`test/core/database/build_number_matches_schema_test.dart`).
- DDL only inside `onUpgrade`, one `if (from < N)` block per version. Data
  backfills go through a separate service, never inline with DDL.
- Secrets (Home Assistant token, assistant API keys) are stored with
  `flutter_secure_storage`, never in the database.

## Home Assistant rules learned the hard way

- Never gate a feature on `lastSuccessfulConnection`; a device living on the live
  WebSocket path never records one.
- A backfill pass that fails wholesale must not arm the retry throttle; cold launch
  races the network coming up.
- Freshness uses the time the app received a value, not HA's `last_updated`,
  which only advances when a value changes.
- Validate a mapped entity's value against a plausible range before storing it.
  A CPU temperature mapped as air temperature poisons every derived number.
